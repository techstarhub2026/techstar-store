Part TwoReference Platform Analysis

This part records what the reference platform actually is. It is the factual base for every requirement that follows. Nothing here is inferred from marketing material or from what an electronics store "usually" does.

2.1 Runtime architecture

LayerObserved
Client frameworkVue 3, compiled with webpack 5. Build name bafredo-client. Composition API with <script setup> (evident from the compiled __name component descriptors).
RoutingVue Router 4, history mode, 25 public routes plus a nested /dashboard tree of 26 admin routes. All non-critical routes lazily loaded — 65 async chunks.
StatePinia, 14 stores. Cart and wishlist mirrored into localStorage; auth session persisted to localStorage under the key authDetails as {isAuthenticated, user, token}.
CSSBootstrap 5.2.2 loaded from jsDelivr CDN, plus 43 component-scoped stylesheets. Single typeface: Montserrat. Brand green #246345.
APISame-origin, mounted at /api. Base URL resolved at runtime: production host → https://www.bafredo.co.tz/api; otherwise window.location.origin. A development constant https://dev.bafredo.co.tz/api and a http://localhost:2700 literal are both still present in the shipped production bundle.
Server data storeMongoDB with Mongoose. Proven by every API response carrying _id in 24-character hex ObjectId form plus a Mongoose __v version key, and by aggregation-shaped responses where _id holds a grouping key (a product name, or a month number) rather than a document identifier.
RealtimeSocket.IO client, connecting to the API origin with auth: { _id }. Used for admin notification of new orders.
MediaCloudinary. Every image is stored once as WebP and served through three named transformations — see §2.5.
AnalyticsGoogle Analytics 4 (G-6MDZJR4J3C), loaded in the HTML shell. An Ahrefs site-verification meta tag is present.
AuthBearer token in localStorage. Social sign-in via server-side redirect endpoints /auth/google and /auth/facebook, returning to a client route /OAuthRedirecting that extracts the token.
Security observations carried forward as requirements Three things in the reference implementation must not be reproduced. (1) The session token is kept in localStorage, which is readable by any injected script; TechStar uses an httpOnly refresh cookie plus a short-lived in-memory access token (§11.2). (2) Development hostnames and a localhost port are shipped in the production bundle, disclosing internal topology; TechStar's build strips non-production configuration (§22.2). (3) The realtime socket authenticates by passing a raw user identifier as auth._id, which is a guessable value rather than a proof of identity — anyone can claim to be any user; TechStar authenticates sockets with the access token (§17.5).

2.5.1 SKU scheme

The reference platform uses a strict positional SKU, and it is worth keeping because it makes physical stock control in a component store tractable.

Category      2 digits   e.g. "05"      Sensors & Conditioning Boards
Subcategory   4 digits   e.g. "0510"    = category "05" + sequence "10" (Voltage)
Product       7 digits   e.g. "0510003" = subcategory "0510" + sequence "003"

Verified examples
  0111004   Hardware Dev Tools (01) > Raspberry Pi boards (0111) > item 004
  0510003   Sensors (05) > Voltage (0510) > item 003

2.5.2 Media transformations

Each image is stored once and exposed at three sizes. Every product, banner, service and partner record carries the same triple.

KeyTransformationUsed by
smthumbnail, width 200Cart and wishlist rows, gallery thumbnails, admin table rows
mdthumbnail, width 600Product cards in grids and carousels
lgoriginalProduct detail hero, banner artwork
Do not copy this detail The reference platform's sm and lg transformation URLs pin a stale version segment (v1668076879) while md omits it, so the three sizes are not guaranteed to be the same asset after a re-upload. It also applies a face-detection crop gravity (g_face) to photographs of circuit boards, which is meaningless here and can crop badly. TechStar's pipeline (§15.2) uses content-addressed derivative names and centre-weighted crops.

2.7 Defects and gaps in the reference platform

Feature parity is the goal; bug parity is not. These are concrete faults observed in the reference implementation. Each is listed with the section where TechStar's corrected behaviour is specified. Fixing them costs little at design time and is expensive later.

#DefectConsequenceFixed in
R1Product detail URLs use the product name as the path segmentRenaming a product breaks every inbound link, every shared URL and every search-engine result. Names containing /, %, # or & require double-encoding; the code contains a manual %25 unescape to work around this. Two products may not share a name, ever.§6.6
R2Variants are separate product rows re-grouped by name at read timeGrouping is a string join. A trailing space or a case difference silently splits one product into two. Observed in live data: "Raspberry Pi 4 4gb Model B Starter Kit " carries both double spaces and trailing whitespace.§12.2
R3addToCart computes an index, then pushes when the item is absent, then indexes with the stale valueThe first add of any item stores quantity 1 but skips the increment branch; subsequent adds work. Quantity handling is inconsistent between first and later additions.§12.5
R4visitProduct deduplicates with find(e => { e.name }) — a block body with no returnThe predicate always returns undefined, so the cache never hits and every visit refetches and appends a duplicate entry, growing memory for the session's lifetime.§19.3
R5Category and subcategory stores never invalidateAn administrator adding a category cannot see it in the storefront navigation without a hard reload.§19.3
R6Cart holds a price copied at add-to-cart timeIf price or stock changes while an item sits in the cart, the customer checks out against a stale price. There is no re-validation before order creation.§12.5
R7No stock check between add-to-cart and order placementOverselling. The product page shows available stock but nothing enforces it downstream.§12.4
R8Success is asserted by exact status code (if (201 !== status) throw)A 200 from a proxy, or a 204, is treated as failure. Inconsistent across stores: services and partners expect 201 on delete, which no correct server would return.§10.1
R9Session token in localStorage; socket authenticated by raw user idToken theft via any injected script; socket identity is spoofable by anyone who knows or guesses an id.§11.2, §17.5
R10Development hostnames and localhost:2700 shipped in the production bundleInternal topology disclosure.§22.2
R11Empty subcategories rendered in the mega-menu with a "0" badgeThirteen dead ends in primary navigation.§7.1.3
R12Bulk category delete cascades to all subcategories and all their productsOne mis-click destroys a large part of the catalogue. The confirmation prompt warns, but the action is irreversible and unaudited.§9.5, §14.19
R13No customer management screen despite a "Customers" sidebar entryAdministrators cannot view, search, suspend or assist an individual customer.§14.7
R14Two identical footer columns both headed "COMPANY INFORMATION"Visible on every page. Cosmetic, but it is on every page.§7.1.5
R15Typos in shipped UI: "No products to diplay", "Sarturday", "Opps!"Erodes trust at exactly the moments the user is already unsure.Appendix C
R16A product with price 0 is purchasable ("R-DRONE NAKED — TZS 0" is live)Free orders. No validation prevents a zero or negative price.§12.3
R17No pagination on the full catalogue grid — limit=10000A single response carrying the entire catalogue. Fine at 617 products, fails at 6,000.§16.5
R18Order cancellation is DELETE /order/:idCancellation should be a state transition that preserves the record, not a deletion. Financial and audit history is lost.§12.7
