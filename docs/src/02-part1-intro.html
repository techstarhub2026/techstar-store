Part OneIntroduction, Scope and Method

1.1 What this document is

This is the complete build specification for TechStar Store, an online shop selling STEM kits, educational electronics and electronic components, parts, tools and instruments. It defines the product, the user experience, the visual system, the database, the API, the business rules, the administration console and the operational plan in enough detail that an engineering team can implement the platform without needing to invent behaviour.

The brief was explicit: build a store that matches bafredo.co.tz feature-for-feature and screen-for-screen, rebranded as TechStar Store, on React and MySQL, with an administration area that can create, read, update and delete every object in the system. This document is written to that brief.

Every statement about the reference platform in Part Two is derived from direct observation of the live site — its JavaScript bundles, its rendered DOM, its stylesheets and its public API responses — not from assumption. Where the reference platform's behaviour could not be observed because it sits behind an authenticated wall, this document says so explicitly and states the design decision TechStar will take instead.

Reading order Parts 1–3 are for everyone: they define what is being built and why. Parts 4–8 are for designers and frontend engineers. Parts 9–13 are for backend engineers. Part 14 is for whoever builds the admin console — it is the largest single chapter because the brief asks for total CRUD coverage. Parts 15–22 are cross-cutting. Part 23 is for whoever plans the work. The appendices are lookup tables you will return to during implementation.

1.3 How the reference platform was analysed

The reference site is a client-rendered single-page application. Its served HTML is an empty shell, so ordinary page fetching reveals nothing. Five techniques were used in combination.

1.3.1 Bundle extraction

The application ships one entry bundle (app.js, 144 KB), one vendor bundle (2.0 MB) and 65 lazily loaded route chunks (2.4 MB total). The webpack chunk manifest inside the entry bundle maps numeric chunk IDs to content-hashed filenames; that manifest was parsed to enumerate and download all 65 chunks. Because production Vue builds preserve string literals verbatim, every route path, API path, form label, validation message and toast string survives minification intact.

1.3.2 Route and store recovery

Vue Router route records and Pinia store definitions were located by pattern in the entry bundle and extracted with brace-matched slicing, yielding 14 complete store definitions with their state shapes and action bodies. Because each action contains its own HTTP call, the store bodies double as an API contract.

1.3.3 API surface reconstruction

All calls flow through one helper of the form request(path, method, body). Matching that call signature across the entry bundle and all 65 chunks recovered 90 distinct endpoint/verb pairs, including path parameters and query strings, listed in full in §2.3.

1.3.4 Live API probing

The recovered public read endpoints were called directly. This produced real response payloads with real field names, types and nesting — the difference between guessing a schema and knowing one. Authenticated endpoints returned 401 and were not pursued; no credentials were used, no accounts were created, and no write operation was ever sent.

1.3.5 Headless rendering

Key pages were rendered in headless Chrome with a 20-second virtual-time budget, then captured both as full-page screenshots and as complete post-hydration DOM dumps. The DOM dumps give exact element nesting, utility classes, ARIA attributes and copy; the screenshots give proportion, rhythm and colour.

Scope of observation The reference platform's administration console at /dashboard/* is behind authentication and was never entered. Everything Part 14 says about administration screens is reconstructed from the shipped client code for those screens — table column headers, form fields, modal titles, validation messages, bulk-action confirmation prompts and empty states are all recovered strings. What could not be recovered is server-side admin behaviour: exact permission rules, audit trails, and any admin-only response fields. Those are specified fresh in this document as TechStar's own design, and are marked as such.

1.4 Assumptions and decisions register

Where the brief left a choice open, a decision was made rather than a question asked, so that implementation is not blocked. Each is recorded here with its rationale and the alternative that was rejected. Any of these can be reversed; the cost of reversal is noted.

1.5 Legal and originality boundary

Building a competing store with the same feature set, the same information architecture and the same interaction patterns is ordinary commercial practice, and this document specifies exactly that. Three things must nevertheless be original to TechStar, and the specification is written on that basis:

  • Brand assets. Name, logo, wordmark, tagline and colour identity are TechStar's own. Part 5 defines a distinct palette rather than reusing the reference platform's.
  • Editorial and legal copy. Product descriptions, About, FAQ, Privacy Policy, Terms & Conditions and blog articles must be written for TechStar. This document specifies the structure of those pages — section headings, ordering, field lengths — and never supplies the reference platform's prose as body text. Legal pages in particular must be drafted or reviewed against Tanzanian consumer and data-protection law for TechStar's own operations.
  • Catalogue content. Product names, photography and descriptions must be TechStar's own or supplied under licence by TechStar's distributors. What Appendix A reproduces is the taxonomy — a category and subcategory tree for electronic components — which is an industry-standard classification and the right starting shape for any electronics retailer, not proprietary content.
  • Registration identifiers. The reference platform publishes its own TIN and certificate of incorporation numbers in its footer. TechStar's footer must carry TechStar's own registration details or none at all.

1.6 Glossary

TermMeaning in this document
Reference platformbafredo.co.tz, the site TechStar Store is specified to match.
Product groupA named product as a shopper perceives it — one card in a grid, one detail page. May contain one or many variants.
VariantA specific purchasable configuration of a product group, with its own price, stock and SKU. A resistor product group might have variants for 220 Ω, 1 kΩ and 10 kΩ.
AttributeA named dimension along which variants differ — Resistance, Voltage, Colour, Capacity.
SKUStock keeping unit. A structured 7-digit code, defined in §12.1.
Lipa NambaTanzanian mobile-money merchant till number. Customers push funds to it from M-Pesa, Tigo Pesa (Mixx by Yas), Airtel Money or Halopesa.
Delegated paymentPlacing an order and nominating a third party — a parent, employer or sponsor — to pay it. Called "friend payment" on the reference platform.
Minor unitsThe smallest indivisible unit of a currency. All money in the database is stored as an integer count of minor units to avoid floating-point error.
Soft deleteMarking a row as deleted with a timestamp rather than removing it, so history and foreign keys survive.
FacetA filterable attribute in the catalogue — category, subcategory, price band, availability.
