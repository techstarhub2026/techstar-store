9.5 Referential integrity and delete semantics

RelationshipOn deleteReasoning
category → subcategoriesRESTRICTA category with subcategories cannot be removed. This is the direct fix for defect R12: the reference platform cascades a category delete through its subcategories and into every one of their products.
subcategory → productsRESTRICTSame reasoning. The admin console offers "move products to another subcategory" as the supported path.
product → variants, images, attributesCASCADEThese have no meaning apart from their product.
variant → order_itemsSET NULLHistorical orders survive; the snapshot columns keep them readable.
variant → cart_itemsRESTRICTForces the deletion path to clear affected carts explicitly and notify their owners, rather than silently emptying a cart.
user → ordersSET NULLFinancial records outlive accounts. The snapshot fields preserve who bought what.
user → sessions, tokens, addresses, cartCASCADEPersonal data goes with the account.
order → items, events, addressCASCADEOnly relevant if an order is ever hard-deleted, which the application never does.
order → paymentsRESTRICTAn order with a recorded payment cannot be deleted, under any circumstances.
media_file → any referenceRESTRICTA referenced file cannot be deleted; the reference count enforces it before the constraint has to.
article → commentsCASCADE
campaign → recipientsCASCADE
Soft delete is the default; hard delete is an operation Every customer-facing and administrator-facing delete sets deleted_at. Rows are removed from the database only by a scheduled purge — 90 days for catalogue entities, never for anything with a financial or audit dimension. The admin console gains a "Trash" view per entity with restore. This one rule converts the reference platform's most dangerous action, a bulk category delete that destroys a swathe of catalogue with no recovery, into a reversible mistake.
