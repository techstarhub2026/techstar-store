Part ThreeProduct Definition

3.1 Vision

TechStar Store is the place a Tanzanian student, hobbyist, technician or engineer goes to find the part they need, understand what it does, and get it delivered or collected — without leaving the country's payment and logistics reality. It sells two adjacent things: STEM — kits, robots, drones, starter bundles, teaching aids — and electronics — components, modules, boards, instruments, tools and consumables.

Those two halves have different buyers with different needs, and the design must serve both:

  • A STEM buyer browses. They arrive without a part number, respond to imagery and bundles, and need to be told what a thing is for. They are served by the home page carousels, the category tree, rich descriptions and "what's in the box" content.
  • An electronics buyer searches. They arrive knowing "74HC14" or "10 kΩ 1/4 W" and want the fastest path from search box to cart, with accurate stock and a clear price. They are served by search quality, SKU structure, variant selection and stock accuracy.

3.4 Primary user journeys

J1 — Browse to purchase, guest, mobile money

Home
  └─ banner "BUY NOW" → Product detail
       └─ select variant (if any) → set quantity → ADD TO CART
            └─ cart off-canvas slides in, badge increments
                 └─ VIEW CART → CHECKOUT
                      ├─ enter name + phone (no account required)
                      ├─ choose shipping method  → cost added to total
                      ├─ if method requires it: shipping details form
                      │    (receiver name, region → district, street, postal code)
                      ├─ choose payment method: Lipa Namba | Cash on delivery
                      ├─ if Lipa Namba: enter paying phone number (255XXXXXXXXX)
                      └─ PLACE ORDER
                           └─ Order confirmation + payment instructions
                                └─ customer pushes funds to Lipa Namba
                                     └─ admin marks payment received
                                          └─ SMS + email confirmation to customer

J2 — Search to purchase, returning customer

Header search "74HC14" → Search results (term logged for analytics)
  └─ Product detail → ADD TO CART → cart merges with server-side cart
       └─ CHECKOUT (identity, address and last shipping method prefilled)
            └─ PLACE ORDER → order appears in /orders immediately

J3 — Delegated payment (school or employer pays)

Customer builds order → CHECKOUT
  └─ enters a delegated payer email address
       └─ PLACE ORDER → order created with status AWAITING_PAYMENT
            └─ payer receives an email containing /friend_payment/:orderId
                 └─ payer opens link (no account needed)
                      └─ sees order summary + payment methods
                           └─ enters payment number → MAKE PAYMENT
                                └─ both customer and payer notified on confirmation

J4 — Administrator fulfils the day

Sign in → Dashboard (today's orders, revenue, low stock)
  └─ Orders → filter "Pending"
       └─ open order → verify payment reference → set status PAID
            └─ set status PROCESSING → pick and pack (stock decremented on PAID)
                 └─ set status SHIPPED → customer notified by SMS
                      └─ set status DELIVERED → order closes

J5 — Administrator adds a product with variants

Products → NEW PRODUCT
  └─ choose subcategory (SKU prefix derived automatically)
  ├─ name, rich-text description, images (drag & drop, max 100)
  ├─ Add Attributes → define columns e.g. "Resistance"
  │    └─ add rows: 220Ω | 500 | 200      (value | price | stock)
  │                 1kΩ   | 500 | 350
  │                 10kΩ  | 500 | 180
  └─ Submit → one product group + three variants, SKUs auto-assigned

3.5 Non-goals for version 1

Stated so that scope stays honest. Each is a deliberate exclusion, not an oversight.

  • Multi-vendor marketplace. TechStar is the single seller. No vendor onboarding, no split settlement.
  • Multi-warehouse inventory. One stock pool. Location-aware stock is a Phase 5 candidate.
  • Multi-currency pricing. Prices are held in TZS. The money column type (§9.1) is chosen so that adding currencies later is additive, not a migration.
  • Card payments. Mobile money and cash cover the market. Card acquiring can be added through the same payment adapter.
  • Native mobile applications. The web experience is specified mobile-first and installable as a PWA (§21.3).
  • Automated courier integration. Shipping is a flat per-method cost, as on the reference platform. Courier APIs are a Phase 5 candidate.
  • Full Swahili translation. Strings are externalised from day one (D10) but only English and the Swahili payment instructions ship in v1.
