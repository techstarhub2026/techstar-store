15.2 Derivative sizes

KeyWidthFitUsed by
sm200 pxcontain, white padCart and wishlist rows, gallery thumbnails, admin table rows
md600 pxcontain, white padProduct cards in grids and carousels
lg1400 px maxinside, no upscaleProduct detail hero, lightbox, banners

All derivatives are WebP at quality 82, with a JPEG fallback generated only if analytics ever show meaningful traffic from browsers without WebP support — as of now, none does. Names are content-addressed: {publicId}-{key}-{checksum8}.webp, so a re-upload can never be served from a stale cache. Cache headers are public, max-age=31536000, immutable.

Two corrections to the reference platform's pipeline It applies a face-detection crop (g_face) to photographs of circuit boards, which is meaningless and occasionally crops the subject out. TechStar uses contain with white padding, so a component photographed on a white background is never cut. And its three sizes carry inconsistent version segments, so they can drift apart after a re-upload; content-addressed names make that impossible.

15.4 Cleanup and orphans

  • media_files.reference_count is incremented and decremented in the same transaction as the referencing row.
  • A nightly job soft-deletes files with zero references older than 24 hours — the delay covers an upload whose form was never submitted.
  • A weekly job hard-deletes soft-deleted files older than 30 days and removes their bytes.
  • A monthly reconciliation compares storage keys against database rows in both directions and reports discrepancies rather than acting on them.
  • Deleting a referenced file is refused by the API before the foreign key has to intervene, with a message naming what references it.

Part SixteenSearch, Filtering, Sorting, Pagination

16.1 Engine choice

MySQL full-text at launch; a dedicated engine only when measurement demands it At 617 products — and at ten times that — MySQL's InnoDB full-text index with the tuning in §9.4 returns results in single-digit milliseconds. Adding Elasticsearch or Meilisearch on day one buys typo tolerance and synonyms at the cost of a second datastore to run, secure, back up and keep in sync. The trigger for revisiting is explicit: the catalogue passes 20,000 products, or the zero-result rate exceeds 15% and is traceable to matching rather than to genuine catalogue gaps. The search service is written behind an interface so the swap is contained.

16.2 Query grammar and ranking

A search runs four passes and returns them in this order, deduplicated. Ordering by relevance means ordering by which pass matched.

PassMatchRationale
1Exact SKU, or exact manufacturer part numberSomeone typing 74HC14 or 0510003 wants that part and nothing else. This pass short-circuits: a hit here returns immediately.
2Name prefix (name LIKE 'term%')Prefix matches are near-certain intent.
3Name containsCatches mid-string matches like "uno" in "Arduino Uno R3".
4MATCH … AGAINST in boolean mode over name, description, brand and MPNFull-text relevance, with name weighted 4×, brand and MPN 2×, description 1×.
RuleSpecification
NormalisationLowercase, trim, collapse whitespace, strip punctuation except -, . and /, which carry meaning in part numbers.
Multi-wordAll terms required (boolean +), then relevance-ordered. "arduino uno" must not return every Arduino.
Short tokensinnodb_ft_min_token_size = 2 with an empty stopword table, so "IC", "DC" and "5V" are searchable.
SuggestionsSpelling suggestions come from a term dictionary built nightly from product names, matched by trigram similarity within an edit distance of 2, and only offered when the original returned nothing.
SynonymsA small hand-maintained table for this trade: resistor ↔ resistance, capacitor ↔ cap, LED ↔ light emitting diode, pot ↔ potentiometer, uC ↔ microcontroller, PSU ↔ power supply. Editable in the admin console.
FiltersApplied as SQL predicates after matching, never in the application layer, so pagination totals stay correct.
HighlightingPerformed client-side on the returned names, so the server does not have to escape and return HTML.

16.3 Facets

Facet counts are computed in one additional aggregate query against the same filtered set, so a count never contradicts the grid beneath it. Price bands are derived from the actual distribution in scope — quartiles rounded to readable boundaries — rather than fixed bands that would be empty for most subcategories.

17.2 SMS

SMS matters more than email in this market — a Tanzanian customer will see an SMS within minutes and an email possibly never. Sent for: order placed, payment confirmed, order shipped, order ready for pickup, and the 36-hour expiry warning. Kept under 160 GSM-7 characters so each is one segment. The adapter interface:

interface SmsProvider {
  send(to: string, message: string, opts?: { senderId?: string })
    : Promise<{ messageId: string; segments: number; cost?: Money }>
  sendBulk(messages: { to: string; message: string }[])
    : Promise<BulkResult>
  deliveryStatus(messageId: string): Promise<DeliveryStatus>
  balance(): Promise<Money>
}

Implementations for Beem Africa and NextSMS, plus a console stub for development. Numbers are canonicalised to 255XXXXXXXXX before sending. A sender ID must be registered with the operators in advance — allow two to three weeks for this in the launch plan, because it cannot be hurried and blocks go-live.

18.1 Metric definitions

Ambiguity in a metric definition is worse than not having the metric. These are normative.

MetricDefinition
RevenueSum of total_amount for orders whose paid_at falls in the period. Recognised on payment, not on placement — an unpaid order is not revenue.
OrdersCount of orders whose placed_at falls in the period, excluding EXPIRED. Cancelled orders are included, because cancellation rate is itself a signal.

18.2 Aggregation approach

Dashboard queries run against a small set of hand-written SQL statements using window functions and CTEs — this is where the ORM is set aside deliberately. Two things keep them fast: a date-spine CTE so that periods with no orders still produce a zero row (otherwise charts silently skip days), and the denormalised paid_at, shipped_at and delivered_at columns on orders, which avoid joining the event log for every chart.

-- Revenue and order count by month, last 12 months, with zero-filled gaps
WITH RECURSIVE spine AS (
  SELECT DATE_FORMAT(DATE_SUB(CURDATE(), INTERVAL 11 MONTH), '%Y-%m-01') AS d
  UNION ALL
  SELECT DATE_ADD(d, INTERVAL 1 MONTH) FROM spine
  WHERE d < DATE_FORMAT(CURDATE(), '%Y-%m-01')
)
SELECT  DATE_FORMAT(s.d, '%Y-%m')                AS bucket,
        COALESCE(SUM(o.total_amount), 0)         AS revenue,
        COUNT(o.id)                              AS orders
FROM    spine s
LEFT JOIN orders o
       ON o.paid_at >= s.d
      AND o.paid_at <  DATE_ADD(s.d, INTERVAL 1 MONTH)
      AND o.payment_status = 'paid'
GROUP BY bucket
ORDER BY bucket;

Results are cached in Redis for 5 minutes, keyed by period and filter. Above roughly 100,000 orders, a nightly rollup into a daily_metrics table replaces the live aggregation; the API contract does not change when that happens.

18.3 Charts

Chart.js, following the house rules: one hue family for a single series; the categorical palette only when series are genuinely unrelated; axes always labelled with units; the y-axis always starting at zero for bar charts; no more than six series on one chart; and a "View as table" toggle on every chart so the data is reachable without sight. Money on axes is abbreviated (TZS 1.2M) and shown in full in tooltips.
