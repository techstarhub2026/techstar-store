19.3 Data fetching

ConcernRule
Query keysStructured arrays: ['products', {subcategory, sort, page}]. Built by a keys factory per feature so no two call sites can disagree.
Stale timesCategories and settings 30 min · products 5 min · cart 0 (always fresh) · orders 1 min · admin lists 0.
InvalidationEvery mutation declares the key prefixes it invalidates. A mutation with no invalidation list fails review.
Optimistic updatesCart quantity, wishlist toggle, admin active toggles and reordering. Always with a rollback path.
PrefetchProduct detail is prefetched on card hover or focus after a 150 ms delay; the next catalogue page is prefetched when the current one is 80% scrolled.
RetryTwice with exponential backoff for GET; never for POST, PATCH or DELETE, which is what idempotency keys are for instead.
Error handlingA single API client maps error codes to typed errors; 401 triggers one queued refresh and a replay; 403 and 5xx surface through the error boundary.

19.4 Forms and validation

One Zod schema per form, imported from packages/contracts — the same object the server validates against. Mode is onTouched then onChange once a field has errored. Server-side field errors from a 422 are mapped back onto form fields by name so they appear in the same place as client-side ones. Submit is disabled while pending and while the form is pristine. Every form guards against navigation with unsaved changes.

19.5 Error boundaries

Three levels: a root boundary rendering the 500 page with the request id; a route-level boundary so one failing route does not blank the shell; and section-level boundaries around each independently loaded home-page rail (§7.2.2), so one failed request degrades one section. Boundaries report to the error tracker with the request id, the route and a redacted breadcrumb trail.

19.6 Code splitting and performance

  • Route-level lazy loading for every route; the admin console is a single separate chunk group that a customer never downloads.
  • Heavy libraries are loaded only where used: the rich-text editor, the chart library, FilePond and Leaflet are all dynamic imports.
  • Initial storefront bundle budget: 180 KB gzipped of JavaScript. The reference platform ships a 2 MB vendor bundle on first paint; the largest single contributor is a date library that has a 20× smaller replacement.
  • Images lazy below the fold, eager for the banner and the product hero, always with explicit dimensions.
  • Fonts self-hosted, preloaded, subset, font-display: swap.
  • react-window for any list beyond 200 rows — the admin product table at scale.

19.7 Accessibility

WCAG 2.1 AA is the target and is testable. Landmark regions on every page; one h1 per page with no skipped levels; a visible skip link; focus never lost or trapped except deliberately in modals and off-canvas panels; a visible 2 px focus ring everywhere; all interactive elements reachable and operable by keyboard; 44 px minimum touch targets; live regions for cart changes, search result counts and form errors; no information conveyed by colour alone — every status pill carries text; all images have meaningful alt text or are explicitly decorative; forms use real labels, never placeholders as labels. eslint-plugin-jsx-a11y runs in CI and axe runs against every Storybook story.

19.8 Internationalisation

react-i18next, English shipped, Swahili scaffolded. All copy resolved through t() from day one — retrofitting this into a finished application costs many times what it costs now. Interpolation for names and counts; ICU plurals; dates and money through Intl with the Africa/Dar_es_Salaam zone and the configured currency. The payment instruction blocks ship in both languages immediately (§7.8.1), because that is where a mistranslation costs an order.

20.2 Layering

Strictly one direction: routes → controller → service → repository → Prisma. Controllers know HTTP and nothing about business rules. Services own invariants and transaction boundaries and know nothing about HTTP. Repositories know Prisma and nothing about rules. domain/ is pure and has no imports from any other layer, which is what makes the order state machine, the pricing resolver and the SKU allocator testable without a database. Violations are caught by an import-boundary lint rule.

20.3 Transactions

OperationMust be atomic across
Place orderOrder · items · address · reservations on every variant · stock movements · order event · cart clear · idempotency record
Verify paymentPayment · order payment status and lifecycle · stock deduction · movements · order event · notification enqueue
Cancel orderOrder status · reservation release · movements · order event
Create productProduct · attributes · variants · images · SKU allocation · counter updates on subcategory and category
Delete categoryPrecondition check · soft delete · counter updates · audit record
Approve reviewReview status · product review_count and average_rating · audit record

Rules: lock rows in a consistent order — always ascending by primary key — to avoid deadlock; keep transactions short and never perform network I/O inside one; enqueue side effects rather than executing them, so a failed email never rolls back a paid order; and set an explicit 5-second timeout with a retry for deadlock victims.

20.5 Logging and observability

Structured JSON via pino. Every line carries requestId, userId where known, route, method, status and duration. A serializer redacts password, token, authorization, refreshToken, paymentNumber and any key matching /secret|key|hash/i. Levels: error for failures needing attention, warn for handled anomalies such as a rejected webhook signature, info for business events (order placed, payment verified, campaign sent), debug off in production. OpenTelemetry traces span HTTP, database and queue work, so a slow checkout can be attributed to a specific query.

20.7 Configuration

One config/index.ts parses process.env through a Zod schema at boot and exports a frozen, typed object. A missing or malformed variable stops the process with a message naming the variable — never a runtime undefined three hours later. No other file may read process.env, enforced by lint. 21.3 SEO

The catalogue is the acquisition channel, so the client-rendered decision (D3) must be paid for deliberately. Public routes — home, catalogue, every product, every article, every content page — are prerendered at build time and revalidated on content change, producing static HTML that crawlers and slow devices receive immediately while React hydrates over it. Beyond that: unique title and meta description per page; canonical URLs; Open Graph and Twitter cards with the product image; JSON-LD for Product, Offer, BreadcrumbList, Review, Organisation and FAQPage; a generated sitemap.xml segmented by type and refreshed nightly; a robots.txt excluding /admin, /account, /checkout, /pay and /invoice; 301s from retired slugs; and a PWA manifest with offline support for previously viewed pages.

The production build strips all non-production configuration — no development hostnames, no localhost ports (fixing R10), no source maps served publicly, though they are uploaded to the error tracker. Secrets come from the deployment environment and never from the repository.

22.3 Migrations

Prisma Migrate, forward-only, reviewed in the pull request that needs them. Rules: additive first — add a column nullable, backfill in a job, then enforce NOT NULL in a later release; never drop a column in the same release that stops writing to it; every destructive migration is preceded by a verified backup; and migrations run automatically on deploy with an advisory lock so two instances cannot race.

22.4 Backups and disaster recovery

ItemPolicy
Databasemysqldump --single-transaction nightly, plus binary logs for point-in-time recovery. Encrypted, off-site, 30 daily / 12 monthly / 7 yearly.
MediaNightly incremental sync to off-site object storage.

22.5 Monitoring and runbooks

Uptime checks on /, /api/v1/health and /api/v1/health/deep (which verifies MySQL, Redis and storage). Alerts on: 5xx rate above 1% for 5 minutes; p95 latency above 1 second; queue depth above 1,000; failed webhook count above zero; disk above 80%; MySQL connections above 80% of maximum; SMS balance below the threshold; a failed nightly backup; and any financial-invariant violation. Written runbooks cover payment provider outage, SMS provider outage, database restore, stuck queue, high traffic event, and a suspected security incident — each naming who to call and what to say to customers.

22.6 Local development on XAMPP

The workstation already runs XAMPP, and its MySQL is a perfectly good development database. Start MySQL from the XAMPP control panel, create the techstar schema with utf8mb4, point DATABASE_URL at mysql://root@127.0.0.1:3306/techstar, and run migrations and the seed. phpMyAdmin at localhost/phpmyadmin is then available for inspection. Apache is not needed — Vite serves the front end and Express serves the API. Redis is the one thing XAMPP does not provide: run it under Docker, or under WSL, or use the in-memory queue driver, which is supported for development only.

23.3 Acceptance criteria

A phase is complete only when all of the following hold, not when the screens look finished.

  • Every endpoint in scope has integration tests covering success, validation, unauthenticated, unauthorised and not-found.
  • Every screen in scope has its loading, empty, error and populated states implemented and covered by a Storybook story.
  • Domain logic in scope is at 95% unit coverage.
  • Lighthouse and axe pass at the budgets in §21.2 with no new violations.
  • No high or critical dependency advisory.
  • Every admin action in scope writes an audit record.
  • The relevant end-to-end journeys pass on Chromium and mobile Chrome.
  • Any deviation from this specification is written down, with its reason, in a decision record.
