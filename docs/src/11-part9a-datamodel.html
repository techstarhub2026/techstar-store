Part NineData Model — MySQL

9.1 Modelling principles

These rules are applied without exception across all 50 tables. Where a rule differs from what the reference platform does, the reason is given — the reference platform stores documents in MongoDB, and a direct transliteration of that shape into MySQL would inherit its defects.

PrincipleRule and rationale
Primary keysBIGINT UNSIGNED AUTO_INCREMENT. Compact, ordered, and ideal for InnoDB's clustered index. Public identifiers are separate: slugs for catalogue entities, human-readable numbers for orders and invoices, and random tokens for shareable links. A primary key is never exposed in a URL (§6.6).
Public identifiersEvery entity that appears in a URL carries either a slug VARCHAR(96) with a unique index, or a formatted number such as TS-2026-000148. This is what makes defect R1 structurally impossible.
MoneyBIGINT holding minor units — for TZS, whole shillings, since TZS has no subunit in practice. Never FLOAT or DOUBLE. Every money column is named with an _amount suffix and is accompanied by a currency CHAR(3) on the owning row wherever the value is customer-facing, so a future multi-currency change is additive.
Timestampscreated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) and updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3) on every table. All stored in UTC; the application converts to Africa/Dar_es_Salaam (UTC+3) for display. DATETIME not TIMESTAMP, to avoid the 2038 limit.
Soft deletesdeleted_at DATETIME(3) NULL on every entity a customer or an order can reference. A deleted product must still render correctly inside a three-year-old order. Queries filter deleted_at IS NULL by default through a Prisma middleware, with an explicit escape hatch for the admin console's trash view.
Character setutf8mb4 with utf8mb4_0900_ai_ci collation, database-wide. Product names contain ®, µ, Ω and emoji appear in reviews; utf8 (three-byte) would truncate them.
EngineInnoDB throughout. Foreign keys and transactional integrity are required by the order and stock logic in Part 12.
EnumerationsVARCHAR with a CHECK constraint, not MySQL's ENUM. Adding a value to a native ENUM rewrites the table; a check constraint is altered cheaply, and the values stay legible in a dump.
BooleansTINYINT(1) NOT NULL DEFAULT 0. Named affirmatively — is_active, never is_not_disabled.
NullabilityNOT NULL is the default. NULL is used only where "unknown" is genuinely different from "empty" — a guest order's email is NULL; a product with no description holds ''.
Denormalised countersproduct_count, order_count, review_count, average_rating are maintained in the same transaction as the fact that changes them, never recomputed on read. The reference platform does the same and it is right — but it must be transactional, or the counts drift.
SnapshotsOrders and invoices store a copy of the name, SKU, price and attributes at the moment of purchase, alongside a nullable reference to the live entity. An order must be reprintable after the product is renamed, repriced or deleted. This is not redundancy; it is the correct model for a financial record.
Namingsnake_case, plural table names, singular column names, foreign keys as <singular_table>_id. Indexes named idx_<table>_<cols>, uniques uq_, foreign keys fk_<table>_<ref>.

9.3.3 oauth_accounts

id · user_id FK CASCADE · provider VARCHAR(20) CHECK IN ('google','facebook') · provider_user_id VARCHAR(191) · email VARCHAR(255) NULL · raw_profile JSON NULL · linked_at DATETIME(3). Unique on (provider, provider_user_id); index on user_id. A user may link both providers.

9.3.4 sessions

id · user_id FK CASCADE · refresh_token_hash CHAR(64) UNIQUE (SHA-256 — the raw token is never stored) · user_agent VARCHAR(255) · ip_address VARBINARY(16) · expires_at DATETIME(3) · revoked_at DATETIME(3) NULL · replaced_by_id BIGINT NULL (rotation chain, §11.2). Indexes on (user_id, revoked_at) and expires_at for the cleanup job.

9.3.5 email_verification_tokens and password_reset_tokens

Identical shape: id · user_id FK CASCADE · token_hash CHAR(64) UNIQUE · expires_at DATETIME(3) · used_at DATETIME(3) NULL · requested_ip VARBINARY(16). Verification tokens live 24 hours, reset tokens 60 minutes. Issuing a new token invalidates all outstanding ones for that user.

9.3.7 categories

id · name VARCHAR(120) NOT NULL · slug VARCHAR(96) UNIQUE · sku_code CHAR(2) UNIQUE (the two-digit prefix, §12.1) · description VARCHAR(500) NULL · image_id FK → media_files NULL · position INT NOT NULL DEFAULT 0 (manual ordering) · subcategory_count INT UNSIGNED NOT NULL DEFAULT 0 · product_count INT UNSIGNED NOT NULL DEFAULT 0 · is_active TINYINT(1) NOT NULL DEFAULT 1 · deleted_at. Indexes: uq_categories_slug, uq_categories_sku_code, idx_categories_position.

9.3.8 subcategories

id · category_id FK → categories RESTRICT · name VARCHAR(140) · slug VARCHAR(96) UNIQUE · sku_code CHAR(4) UNIQUE · description VARCHAR(500) NULL · image_id NULL · position INT · product_count INT UNSIGNED · is_active TINYINT(1) · deleted_at. Indexes: uq_subcategories_slug, uq_subcategories_sku_code, idx_subcategories_category.

Why exactly two levels A general tree with a self-referencing parent is more flexible and worse here. The SKU scheme is positional and assumes two levels; the mega-menu is a two-panel design that assumes two levels; and the observed taxonomy — 17 categories, 102 subcategories — has never needed a third. Two explicit tables give simpler queries, cheaper counts and stronger constraints. If a third level is ever required, it is an additive migration, not a redesign.

9.3.10 product_slug_history

id · product_id FK CASCADE · slug VARCHAR(96) UNIQUE · retired_at. Looked up on a 404 to serve a 301 to the current slug. Retired slugs are reserved forever and can never be claimed by another product.

9.3.11 product_images

id · product_id FK CASCADE · media_file_id FK RESTRICT · variant_id BIGINT NULL FK SET NULL (an image may belong to one specific variant) · alt_text VARCHAR(255) NULL · position INT NOT NULL DEFAULT 0. Unique on (product_id, media_file_id); index on (product_id, position).

9.3.12 product_attributes

The attribute columns a product's variant matrix defines. id · product_id FK CASCADE · name VARCHAR(80) ("Resistance", "Capacity", "Colour") · position INT · unit VARCHAR(20) NULL ("Ω", "µF", "mm"). Unique on (product_id, name).

9.3.14 variant_attribute_values

variant_id FK CASCADE · product_attribute_id FK CASCADE · value VARCHAR(120) NOT NULL. Composite PK on (variant_id, product_attribute_id); index on (product_attribute_id, value) for future attribute faceting.

9.3.15 tags and product_tags

tags: id · name VARCHAR(60) · slug VARCHAR(60) UNIQUE. product_tags: product_id · tag_id, composite PK, both CASCADE. Tags feed search boosting and curated collections. The reference platform has a tags array on every product and never populates it; here it is at least usable.
