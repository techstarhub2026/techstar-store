14.18 Audit log

Read-only. Columns: Timestamp · Actor · Action · Entity type · Entity · IP address · Request id. Filterable by actor, action, entity type, entity and date range; cursor-paginated because it grows without bound. Expanding a row shows a field-level diff of before and after. What is not logged: read access to non-personal data, which would swamp the useful signal.

14.19 The universal CRUD contract

Every module above conforms to this. It is what makes "full CRUD on anything" a coherent promise rather than fifteen slightly different screens.

14.19.1 Create

  • Reached from a primary "New {entity}" button in the page header, or from a "+" in an empty state.
  • Modal for entities with 6 or fewer fields; a full page for anything larger.
  • Required fields marked with an asterisk and an explanatory legend. Optional fields are labelled "(optional)" rather than left ambiguous.
  • Validation on blur, then live once a field has errored, then in full on submit. Submit is disabled until dirty and valid.
  • On success: a toast "{Entity} created", and navigation either to the new record or back to the list with the new row highlighted for three seconds.
  • "Save and add another" wherever bulk entry is realistic — products, categories, subcategories, FAQs.

14.19.2 Read

  • Every list is a DataTable (§8.4.1) with search, filters, sort, pagination and density, all reflected in the URL so a filtered view is shareable with a colleague.
  • Every list has a specified empty state naming the primary action.
  • Every detail screen carries created and updated timestamps, the creating and last-updating actor, and an audit panel.
  • Every list offers CSV export of the current filtered set, capped at 50,000 rows and delivered as a queued job with an email link when large.

14.19.3 Update

  • Same form as create, prefilled, with the entity name in the heading.
  • Only changed fields are sent; the payload is a partial.
  • Optimistic concurrency: the form carries the record's updatedAt; a mismatch returns 409 and the UI offers "Reload and reapply my changes" with a field-level diff of what someone else altered.
  • Navigating away with unsaved changes prompts.
  • Inline editing is offered only for single scalar fields where it is genuinely faster — position, active flag, stock.

14.19.4 Delete

RuleSpecification
Soft by defaultSets deleted_at. Recoverable from the entity's Trash view for 90 days.
ConfirmationAlways. The dialog names the specific record — "Delete Arduino Uno R3?" — never "Delete this item?".
Consequences statedThe dialog lists what else is affected and the counts: "This product has 3 variants and appears in 2 open carts."
Blocked deletesWhere §9.5 says RESTRICT, the dialog explains why and offers the supported alternative rather than a bare refusal.
Bulk deletesRequire typing the exact count to confirm — "Type 14 to confirm" — using ConfirmDialog's requireTyping mode. Slow enough to interrupt an automatic click, which is the point.
UndoThe success toast offers "Undo" for 8 seconds on single soft deletes.
Hard deleteAvailable only from the Trash view, only to owner, and never for orders, payments, invoices or audit records.
AuditDeletion writes the full prior state to audit_logs.before, so a hard-deleted record can still be described even when it can no longer be restored.
