Deliberate divergences from the reference route map
  • /product/:slug replaces /product/:name. Fixes defect R1 — see §6.6.
  • /products/c/:slug and /products/s/:slug replace the single ambiguous /products/:id, which could only ever filter by subcategory and gave no way to view a whole category.
  • /admin replaces /dashboard. Plainer, and it frees "dashboard" to mean the analytics page rather than the whole console.
  • /pay/:paymentToken replaces /friend_payment/:orderId. Handing a raw order identifier to a third party lets anyone with an order id open a payment page; a single-purpose signed token does not (§12.9).
  • /invoice/:invoiceToken likewise replaces a raw-id URL: invoices contain a customer's name, address, phone and purchase history and must not be enumerable.
  • /cart exists as a real page, not only an off-canvas panel. The panel remains the primary surface; the page is what a mobile user gets, and what a shared or bookmarked link resolves to.
  • /admin/comments, /admin/reviews, /admin/staff, /admin/audit-log and /admin/customers are new, closing gaps R13 and R12.

6.4.2 The SHOP mega-menu

A two-panel dropdown, 720 px wide, elevated with shadow 2.

  • Left panel, 7 of 12 columns. All categories as a vertical list, each row showing the category name and a right-aligned chevron. Hovering or focusing a row loads that category's subcategories into the right panel; the row highlights with --ts-primary-tint. Clicking navigates to the category page.
  • Right panel, 5 of 12 columns, separated by a left border. The hovered category's subcategories, each with a small primary-green pill showing its product count. Clicking navigates to the subcategory page.
  • Default state. On open, the first category is pre-selected so the right panel is never empty.
  • Keyboard. ↑/↓ move through categories; → enters the subcategory panel; ← returns; Enter navigates; Esc closes and returns focus to the SHOP trigger.
Fixing R11 Subcategories with zero products are omitted from the mega-menu rather than shown with a "0" badge. Categories whose every subcategory is empty are omitted too. They remain fully visible and editable in the admin console — this rule affects storefront navigation only, and is driven by the maintained product_count column (§9.3).

6.4.3 Header, mobile (< md)

  • Single 64 px bar on --ts-ink: hamburger, compact logo mark, search icon, wishlist, cart.
  • The hamburger opens a left off-canvas: Home · Products · Shop (an accordion of categories, each expanding to its subcategories) · Support · Services · then account links.
  • The search icon opens a full-screen modal with an autofocused field and live suggestions.
  • The utility bar is hidden; its phone and email move into the off-canvas footer.

6.5 Route guards

GuardApplies toBehaviour when it fails
requireAuth/account/*Open the auth modal with the intended route stored as nextRoute; on success, navigate there. Never a bare redirect to a login page — the reference platform's modal-based pattern is better and is kept.
requireCart/checkoutRedirect to /cart with an informational toast, "Your cart is empty."
requireStaff/admin/*If unauthenticated, redirect to / and open the auth modal. If authenticated but not staff, render a 403 page with no navigation hints — do not confirm that /admin exists.
requirePermission(p)each admin routeRender a 403 panel inside the admin shell, listing whom to ask for access.
requireToken/pay/:t, /invoice/:tRender "This link is no longer valid" with a contact route. Never reveal whether the token was wrong, expired or already used.
requireOrderAccess/order/confirmation/:nAccessible to the order's owner, or to any session holding the one-time confirmation token issued at placement — this is what lets a guest see their own confirmation.
Guards are convenience, not security Every guard above exists to give the user a sensible experience. None of them protects data: the client bundle is public and any route can be entered directly. Authorisation is enforced server-side on every request, per §11.5. A route guard that has no matching server-side check is a vulnerability, not a feature.

6.6 URL and slug rules

Fixing defect R1 properly requires a stated rule, not just a different path shape.

RuleSpecification
Slug generationLowercase; transliterate accents to ASCII; replace every run of non-alphanumeric characters with a single hyphen; trim leading and trailing hyphens; collapse repeats; truncate to 80 characters at a hyphen boundary.
UniquenessEnforced by a unique index. On collision, append -2, -3, … until free.
StabilityA slug is generated once at creation and never regenerated when the name changes. This is the whole point: renaming "Arduino Uno R3" to "Arduino Uno Rev3" must not break the URL.
RenamingEditing a name offers an optional "update the URL" checkbox, default off. If chosen, the old slug is written to product_slug_history and served as a 301 redirect to the new one, permanently.
Identifier in URLOnly slugs appear in public URLs. Numeric primary keys never do — they leak catalogue size and invite enumeration.
Tokenised URLs/pay/:t and /invoice/:t carry a 32-byte random token, base62-encoded, stored hashed. Payment tokens are single-use and expire after 14 days; invoice tokens are revocable from the admin console.
Canonical formEvery page emits a <link rel="canonical">. Trailing slashes are stripped; uppercase paths 301 to lowercase; query parameters that do not change content (campaign tags, utm_*) are excluded from the canonical URL.
Query parametersCatalogue state lives in the query string so a filtered view is shareable and survives a refresh: ?page, ?sort, ?minPrice, ?maxPrice, ?inStock, ?q. Defaults are omitted rather than written explicitly.
Reserved slugsadmin, account, api, auth, cart, checkout, search, products, product, blog, services, invoice, pay, new, edit may not be used as any entity slug.
