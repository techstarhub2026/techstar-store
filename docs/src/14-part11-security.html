Part ElevenAuthentication, Authorisation and Security

11.1 Identity model

One users table holds both customers and staff, distinguished by account_type and by the roles attached to them. Two tables would duplicate authentication, password reset, session handling and profile management for no benefit, and would make "promote this customer to staff" a data migration.

ConceptDefinition
IdentifierA user is reachable by email, by phone, or by both. Login accepts either in a single field, as the reference platform does; the server decides which by shape. At least one must exist, enforced by a check constraint.
CredentialA password hash, an OAuth link, or both. A user who registered with Google and later sets a password holds both and may use either.
GuestNo account. Identified within a session by a guest_token cookie that owns a cart and a wishlist. A guest may place an order; the order stores their name and phone directly.
Staffaccount_type = 'staff' plus at least one role. Staff sign in through the same modal; the admin console appears in their account menu.
RoleA named bundle of permissions. Users may hold several; effective permissions are the union.
PermissionAn atomic capability string, resource.action. This is the unit checked at every guard.

11.2 Token strategy

The single most important divergence from the reference platform The reference platform stores its bearer token in localStorage (defect R9). Any script that executes on the page — an injected third-party tag, a compromised dependency, a stored XSS — can read it and exfiltrate a full session. TechStar splits the session in two so that no single compromise is sufficient.
TokenSpecification
Access tokenJWT, 15-minute lifetime, signed HS256 with a 32-byte secret (or RS256 if the API is ever split across services). Held in memory only — a JavaScript variable inside the auth store, never in localStorage, sessionStorage or a cookie. Claims: sub (user public id), typ, roles, perms, sid (session id), iat, exp, jti. Sent as Authorization: Bearer.
Refresh token32 bytes of cryptographic randomness, base64url, stored server-side as a SHA-256 hash. Delivered as a cookie: HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth; Max-Age=2592000 (30 days). Unreadable from JavaScript by construction.
RotationEvery call to /auth/refresh issues a new refresh token and marks the old one replaced. Refresh tokens are strictly single-use.
Reuse detectionPresenting a refresh token that has already been replaced means it was stolen. The entire session family is revoked immediately, the user is signed out everywhere, and a security email is sent. This is the mechanism that limits the damage of a stolen cookie to a single refresh cycle.
Silent refreshThe client refreshes at 80% of the access token's life, and once on application boot to restore a session after a reload. Concurrent 401s are queued behind a single refresh, then replayed.
RevocationSign-out revokes the current session; password change and reset revoke all others. Revoked session ids are held in a Redis set until their natural expiry, so an unexpired access token cannot outlive its revocation.
Socket authenticationThe Socket.IO handshake carries the access token and is verified server-side. Fixes defect R9's second half: the reference platform authenticates sockets with a raw user id, which anyone can supply.

11.3 OAuth

Google and Facebook, both authorization-code flow with PKCE. Implicit flow is not used under any circumstances.

1  Client → GET /api/v1/auth/oauth/google
2  Server generates code_verifier + state, stores both against a short-lived
   cookie, redirects to the provider
3  Provider → GET /auth/oauth/google/callback?code=…&state=…
4  Server validates state (CSRF), exchanges code + verifier for tokens,
   fetches the profile
5  Account resolution
     a. oauth_accounts row for (provider, providerUserId) exists → sign in
     b. no row, but a verified user has that email → link, then sign in
     c. no row, no match → create the user with email_verified_at set,
        since the provider has already verified it
6  Server issues its own session, redirects to
   /auth/oauth/callback?code=<one-time>
7  Client → POST /auth/oauth/exchange { code } → session established
Why the extra exchange step Redirecting with a token in the URL leaks it into browser history, the Referer header of any subsequent request, and server access logs. The one-time exchange code is valid for 60 seconds, single-use, and bound to the originating browser. Case (b) links only against a verified email — otherwise anyone could claim an account by registering its address at a provider.

11.4 Email verification, password reset, password rules

11.4.1 Email verification

Registration queues a verification email carrying a 32-byte token, hashed at rest, valid 24 hours, single-use. Until verified, the account can browse, buy and pay — verification is not a gate on commerce, which would cost orders — but it is required to write reviews or comments, and the persistent banner (§7.1.5) keeps asking. Requesting a new link invalidates all outstanding ones. Rate limited to 3 per hour.

11.4.2 Password reset

Token of 32 bytes, hashed at rest, valid 60 minutes, single-use. The request endpoint always returns the same response whether or not the address exists, and takes the same measured time either way — a fast negative is as good an oracle as a different message. On success, every session is revoked and a confirmation email is sent to the address on file, so an unauthorised reset is visible to the real owner.

11.4.3 Password rules

RuleSpecification
LengthMinimum 10 characters, maximum 128. Length is the only requirement that reliably increases strength.
CompositionNo mandatory character classes. Forced classes push users toward Password1!; they measurably reduce entropy.
BlocklistRejected against the 100,000 most common passwords and against the user's own email, username and phone.
Breach checkOptional k-anonymity lookup against Have I Been Pwned's range API — only the first five characters of the SHA-1 hash leave the server. Fails open if the service is unreachable.
Strength meterzxcvbn, shown live during registration and change. Advisory, not blocking, beyond the hard rules above.
HashingArgon2id, memory 19 MiB, iterations 2, parallelism 1 — the OWASP baseline. Parameters are stored with the hash so they can be raised later and rehashed on next successful login.
ComparisonConstant-time. On an unknown identifier, a dummy hash is still verified so that response time does not reveal whether the account exists.

11.6 Input validation

LayerSpecification
SchemaEvery endpoint declares Zod schemas for params, query and body in packages/contracts. The middleware replaces the raw request values with the parsed, typed result, so a controller cannot accidentally read an unvalidated field.
StrictnessObjects are strict — an unexpected property is a 422, not silently dropped. This catches typos in client code and blocks mass-assignment.
CoercionExplicit only. Query strings coerce to number or boolean where the schema says so; nowhere else.
NormalisationEmail lowercased and trimmed. Phone stripped to digits and canonicalised to 255XXXXXXXXX, accepting +255…, 0… and 255… as input. Names trimmed with internal whitespace collapsed. Slugs generated per §6.6.
HTMLRich text is sanitised with an allowlist on write and on render. Two independent passes, because a single point of sanitisation is a single point of failure.
SQLPrisma parameterises everything. The few raw queries in Part 18 use $queryRaw with tagged-template parameters; string concatenation into SQL is forbidden and caught by lint rule.
Mass assignmentControllers pass explicit field lists to services. No ...req.body spread into an update, ever — that is how a customer sets account_type = 'staff'.
OwnershipEvery resource read or write verifies the caller owns the row or holds the permission. Never trust an id in a URL to belong to its bearer.
EnumerationSequential ids never appear in URLs (§9.1), so resources cannot be walked.

11.7 Upload security

ControlSpecification
Accepted typesimage/jpeg, image/png, image/webp, image/avif. SVG is rejected — it is a script-execution vector, and vector logos should be converted to PNG on the way in.
Type determinationMagic bytes, not the client's Content-Type and not the file extension. A mismatch between claimed and actual type is a rejection, not a correction.
Size3 MB per file, 30 MB per request, 100 files per product. Enforced by the multipart parser before anything touches disk.
DimensionsMaximum 8000 × 8000 px. Larger images are rejected rather than resized, which stops decompression-bomb attacks.
Re-encodingEvery accepted image is decoded and re-encoded by sharp. The original bytes are never served. This strips any embedded payload and, incidentally, all EXIF including GPS coordinates.
NamingStored under a generated ULID with a canonical extension. The user's filename is retained as metadata only, and never used as a path component.
Storage locationOutside the web root. Served through a handler that sets Content-Type, Content-Disposition: inline, X-Content-Type-Options: nosniff and long-lived immutable cache headers.
ExecutionThe upload directory is configured with execution disabled at the web-server level, belt and braces.
AuthorisationOnly staff with media.upload may upload, except the customer avatar endpoint, which is limited to one file, 2 MB, 1024 px.
Rate30 uploads per hour per user.

11.8 Security checklist

RiskControl
Broken access controlServer-side permission check on every route; ownership check on every resource; no sequential ids in URLs; strict schemas prevent mass assignment; automated tests assert that each admin route rejects a customer token.
Cryptographic failuresTLS 1.2+ only, HSTS with a one-year max-age and preload. Argon2id for passwords, SHA-256 for token storage. Secrets from the environment, never in the repository. Database at rest on an encrypted volume. Backups encrypted with a separately managed key.
InjectionParameterised queries throughout; HTML sanitised twice; no shell interpolation anywhere; JSON body size capped.
Insecure designOrder state machine rejects illegal transitions server-side; stock changes are transactional with a ledger row; payment verification is a separate permission from order handling; idempotency keys on order and payment creation.
Security misconfigurationConfig validated at boot and fails fast; production build strips development hosts (fixing R10); X-Powered-By removed; directory listing off; error responses carry no stack traces; distinct credentials per environment.
Vulnerable componentsnpm audit and Dependabot in CI; the build fails on a high or critical advisory; a monthly patch window; lockfiles committed.
Authentication failuresRate limits and progressive lockout; identical responses for unknown and wrong credentials; refresh rotation with reuse detection; sessions listed and revocable by the user.
Data integrity failuresWebhook signatures verified before processing; every inbound event persisted before it is acted on; Subresource Integrity on the few external assets; CI publishes build provenance.
Logging failuresStructured logs with a request id on every line; authentication events, permission denials, payment verifications and admin mutations all logged; passwords, tokens, card-like numbers and full phone numbers redacted by a logger serializer; audit log is insert-only at the database-privilege level.
SSRFNo endpoint fetches a user-supplied URL. Outbound calls go only to a fixed allowlist of provider hosts.
XSSReact escapes by default; dangerouslySetInnerHTML permitted in exactly one component (§8.2), enforced by lint; CSP without unsafe-inline, using nonces for the few inline scripts; access token never in a readable store.
CSRFRefresh cookie is SameSite=Strict and scoped to /api/v1/auth; all other authentication is a bearer header, which CSRF cannot forge; state-changing requests require Content-Type: application/json, which blocks simple form posts.
Clickjackingframe-ancestors 'none' plus X-Frame-Options: DENY.
EnumerationIdentical responses and timing for unknown accounts, expired tokens and invalid tokens throughout.
Denial of serviceRate limits at several scopes; body and upload caps; query complexity bounded by a maximum page size; slow-query logging with alerting; Nginx connection limits.

11.8.2 Personal data

ObligationImplementation
MinimisationOnly what an order needs: name, phone, and an address when the shipping method requires one. Date of birth, gender and national identifiers are never collected.
Consentmarketing_opt_in is off by default and captured explicitly. Campaign sending excludes anyone without consent or with an unsubscribe timestamp — the reference platform mails every contact, which is a live compliance exposure.
UnsubscribeOne-click, honoured within seconds, present in every campaign email and every marketing SMS.
Access and portabilityA customer may request an export of their personal data; the admin console produces a JSON bundle of profile, addresses, orders, reviews and comments.
ErasureAccount closure anonymises the user row — name replaced with "Deleted user", email and phone nulled, avatar removed — while orders are retained with their snapshot fields for statutory record-keeping. This is the only way to satisfy both obligations at once.
RetentionGuest carts 30 days · search logs 24 months · audit logs 24 months · sessions until expiry · orders and invoices retained per Tanzanian record-keeping requirements, minimum 7 years.
